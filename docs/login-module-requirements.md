# 登录模块需求澄清文档

> 节点：需求澄清  
> 针对项目：ArmBasic（Python 语音助手）  
> 产物：本文件用于统一后续设计、开发与验收对登录模块的理解。

---

## 1. 项目背景与目标

- **背景**：当前仓库（ArmBasic）主要承载语音助手相关能力，本次需新增一套通用的账号密码登录模块，为后续用户体系、权限管理及扩展认证方式打基础。
- **目标**：提供安全、可用、可测试的登录、登出及登录态维持能力。
- **关键名词**:
  - **账号**：用户的唯一标识，可以是用户名、邮箱或手机号（本期需求未限定）。
  - **密码**：经加盐哈希后持久化存储的凭证。
  - **登录态**：服务端确认用户已登录的状态，通过 Cookie/Session 维持。
  - **记住我**：延长登录态有效期的可选机制。
  - **锁定**：因连续登录失败导致账号临时不可用的状态。
  - **验证码 / IP 限流**：防止暴力破解的辅助手段。

## 3. 功能需求

### 3.1 登录入口
- 由客户端（SPA / 移动 App / 外部系统）自行实现登录页面/表单。
- 后端登录 API 在失败次数达到阈值时，返回需要验证码的标识；客户端据此展示验证码。
- 客户端在调用登录接口时，可携带「记住我」开关。

### 3.2 输入校验
- 账号格式校验（非空、长度、合法字符）
- 密码长度与复杂度校验（最小长度、不允许全空）
- 验证码校验（触发时必填）

### 3.3 核心认证流程
1. 接收登录请求（账号、密码、验证码可选）。
2. 检查 IP / 请求级限流。
3. 检查账号状态：是否存在、是否禁用、是否锁定。
4. 验证密码：与加盐哈希存储值比对。
5. 对「账号不存在」和「密码错误」统一返回「账号或密码错误」，避免账号枚举。
6. 认证失败时递增失败计数，达到阈值则要求验证码或锁定账号。
7. 认证成功后重置失败计数，创建会话 / 返回登录凭证。

### 3.4 登录态维持
- 后端以 API 形式返回会话凭证（Session ID / Token），不渲染页面。
- 客户端可选择以下任一方式使用凭证：
  - 通过 `Authorization: Bearer <token>` 请求头携带。
  - 由客户端或服务端写入 HttpOnly、Secure、SameSite 的 Cookie（若客户端为 Web 且选择 Cookie 方案）。
- 普通会话：短有效期（如 30 分钟无操作过期）。
- 「记住我」会话：较长有效期（如 7~30 天），使用独立持久 Token 并与账号绑定。
- 服务端维护会话与 Token 的失效能力。

### 3.5 退出登录
- 客户端调用退出接口时，在 `Authorization` 请求头或 Cookie 中携带当前凭证。
- 服务端使当前会话 / Token 失效。
- 客户端同步清除本地存储的 Token / Cookie。
- 退出后再次访问受保护资源应被拦截。

## 4. 异常与边界场景

| 编号 | 场景 | 期望行为 |
|------|------|----------|
| 1 | 账号不存在 | 统一返回「账号或密码错误」 |
| 2 | 密码错误 | 统一返回「账号或密码错误」，累计失败次数 |
| 3 | 暴力破解 | 失败次数限制 + 验证码 + IP 限流 |
| 4 | 账号被禁用 | 明确提示账号已被禁用 |
| 5 | 账号被锁定 | 提示账号已锁定及解锁方式（如时间/人工） |
| 6 | 会话过期 / 无效 | 返回未登录状态，要求重新登录 |
| 7 | 重复退出 / 非法 Token | 幂等处理，不抛异常，确保当前会话无效 |

## 5. 非功能需求

### 5.1 安全
- 密码必须加盐哈希存储，推荐 bcrypt / Argon2。
- 错误提示不得暴露账号是否存在。
- 对登录接口实施失败次数限制、验证码、IP 限流。
- 传输使用 HTTPS；Token 不应在 URL 中传递，建议放在请求头或 HttpOnly Cookie 中。
- 若使用 Cookie，应设置 HttpOnly、Secure、SameSite。

### 5.2 性能
- 登录接口响应时间目标 ≤ 500ms（P95）。
- 频繁访问的限流计数建议使用高性能存储（如 Redis）。

### 5.3 可用性
- 登录 API 在常见网络环境下可正常访问。
- 关键失败场景有明确、友好的错误码与错误提示。

### 5.4 兼容性
- 后端接口需支持 SPA、移动 App 及外部系统调用。
- 同时支持 Token（`Authorization: Bearer`）和 Cookie 两种凭证携带方式，由客户端按需选择。

## 6. 接口示例（参考）

### 6.1 登录
```http
POST /api/auth/login
Content-Type: application/json

{
  "account": "user@example.com",
  "password": "plain-password",
  "captcha": "1234",
  "rememberMe": false
}
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "code": 0,
  "message": "登录成功",
  "data": {
    "userId": "u-10086",
    "nickname": "User",
    "accessToken": "eyJhbGciOiJIUzI1NiIs...",
    "tokenType": "Bearer",
    "expiresIn": 1800
  }
}
```

```http
POST /api/auth/logout

```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "code": 0,
  "message": "退出成功"
}
```

## 7. 验收标准（可测试）

1. 正确的账号密码可以登录成功并返回有效会话。
2. 错误的账号或密码统一返回「账号或密码错误」，不暴露具体原因。
3. 连续失败 N 次后，再次登录必须校验验证码。
4. 连续失败达到锁定阈值后，账号在一定时间内无法登录。
5. 账号禁用状态下，登录返回「账号已被禁用」提示。
6. 正常会话有效期内可访问受保护接口；过期后访问要求重新登录。
7. 退出登录后，原会话立即失效，无法继续访问受保护接口。
8. 「记住我」会话的有效期显著长于普通会话，且可通过服务端失效。

## 9. 关键设计约束总结

- **安全优先**：密码加盐哈希（bcrypt/Argon2），错误信息统一，失败次数限制 + 验证码 + IP 限流。
- **会话安全**：凭证通过请求头或 HttpOnly Cookie 传递，区分普通会话与「记住我」长会话。
- **可测试性**：每条验收标准对应明确的输入输出，便于自动化测试与评审。
