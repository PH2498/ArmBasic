## 2. 开放问题决策

### Q1：首期目标项目栈是否以 TypeScript/Node 为主？

**决策：否。P0 范围同时覆盖 TypeScript/Node 与 Python 双栈，JUnit XML 作为跨语言兜底格式。**

**理由（SSOT 驱动）：**
- 已验证事实（SSOT）：当前仓库 ArmBasic 为 Python 项目，README 与依赖（`requirements.txt`、`install_mac.sh`、`speech_ai.py`、`run_face_recognition.py`）均指向 Python 栈，无 `package.json` / TS 配置。
- 需求文档 FR1.2 本身已将 **pytest（JUnit XML / JSON report）** 列入 P0 支持范围，并非"仅 TS/Node"。
- 若按"仅 TS/Node"收窄，将导致当前仓库无法验证（违反 AC1/AC5 在本仓库的落地），与目标 G3"支持主流测试框架"相悖。
- 行业最佳实践：测试报告工具的解析层应为框架无关的插件式结构（NFR5），双栈支持是该抽象的自然结果，不增加架构复杂度。

**影响：** M1 里程碑须同时交付 Jest/Vitest(JSON) + pytest(JUnit XML/JSON) + JUnit XML(兜底) 三类解析器，而非先做 TS 再补 Python。

### Q2：报告是否需要中文/英文双语模板，还是仅中文？

**决策：M1 仅提供中文模板；英文模板列为后续迭代候选（M4 之后）。**

**理由：**
- 上下文优先：需求方与当前用户均使用中文交流，README 为中文，目标场景（US1~US4）面向本团队/国内团队同步。
- 安全兜底：单语言模板改动最小、维护成本最低，符合"风险最低、改动最小"。
- 双语模板会引入 i18n 抽象层，超出 M1 核心交付，列为候选而非阻塞。

**影响：** 报告模板硬编码中文文案；`output_format` 配置项仅控制格式（markdown/html/json），不控制语言。

### Q3：是否需要将报告自动推送到 IM / 邮件等渠道？

**决策：不做。** 与需求 2.2 非目标明确一致。

**理由：** 需求文档已将其列为非目标；报告仅落盘并返回路径 + 摘要（FR3.3）。推送能力属后续迭代，本期不纳入设计。

## 3. 隐含歧义点澄清（需求文档未显式提问但影响实现）

### 3.1 执行模式 vs 解析模式（FR1.3）

**决策：双模式均为 P0，须同时交付。**

- 执行模式：Skill 触发测试运行并收集结果（US1/US2/US3）。
- 解析模式：跳过执行，直接解析用户指定结果文件（US4/CI 场景）。
- 理由：US4（CI 复用）为验收要点之一，解析模式是其唯一满足路径，不可降级到 P1。

### 3.2 报告章节顺序与必选项（FR2）

**决策：严格固定六章节顺序，失败分析章节为条件必选。**

顺序固定为：报告头 → 结果摘要 → 失败用例分析（有失败时必选）→ 用例明细 → 覆盖率（若可获取）→ 附录。
- 失败用例分析：仅当存在失败用例时输出；无失败时该章节省略，不影响后续章节。
- 覆盖率：数据存在则呈现总表 + 低于阈值文件清单；不存在则标注"未获取"，其余章节正常（AC5）。
- 用例明细：默认展示全部；超过 200 条时截断并注明截断数。

### 3.3 输出路径与命名（FR3.2）

**决策：默认 `reports/test-report-<YYYYMMDD-HHmmss>.md`；`output_path` 为目录而非完整文件名。**

- 当 `output_path` 指定目录时，文件名按默认模板生成（含时间戳）。
- 当 `output_path` 指定完整文件路径时，按用户指定写入（覆盖默认命名）。
- 时间戳字段为幂等性例外（NFR4：同一结果多次生成，除时间戳外内容一致）。

### 3.4 测试执行失败的诊断边界（FR1.4）

**决策：区分"命令无法运行"与"用例失败"两类。**

- 命令无法运行（如框架未安装、命令不存在、权限错误）：返回明确诊断信息，**不生成报告**（AC4）。
- 用例失败（命令成功执行但有断言失败）：正常生成报告，失败分析章节承载详情。
- 诊断信息须包含：失败原因、建议排查方向、原始命令与退出码。

### 3.5 覆盖率获取开关（FR4.2 `coverage`）

**决策：`auto` = 检测到覆盖率产物则纳入，否则省略并标注"未获取"。**

- `on`：主动触发带覆盖率参数的测试命令（若框架支持）。
- `off`：不采集覆盖率，报告无覆盖率章节。
- `auto`：被动检测已有覆盖率产物（如 `coverage/`、`.coverage`、`coverage-final.json`），存在则解析。

### 3.6 长任务执行策略（R2）

**决策：测试执行交由 Agent 运行时后台任务能力；解析与报告生成在主线程同步完成。**

- 执行模式触发后，长任务走后台执行 + 轮询；解析与渲染（NFR1：≤5s/1000 用例）同步完成。
- 本 Skill 不自带任务调度，依赖宿主 Agent 的后台执行能力。

## 4. 范围基线确认

### 4.1 P0（M1 必交付）
- Jest JSON 解析器
- Vitest JSON 解析器
- pytest JUnit XML / JSON report 解析器
- JUnit XML 跨语言兜底解析器
- Markdown 报告生成（六章节固定结构）
- 执行模式 + 解析模式
- 默认路径 `reports/test-report-<ts>.md`
- 中文模板
- 失败用例分析（条件必选）
- 覆盖率章节（auto 模式被动采集）
- 执行失败诊断（不生成空报告）

### 4.2 P1（M2/M3）
- pytest 深度支持（若 M1 已含则强化）
- `fail_threshold` 结论标记
- HTML 输出
- JSON 伴随产物

### 4.3 非目标（本期不做，显式排除）
- 测试用例自动生成 / 修复
- 报告在线托管 / Web 服务化
- 多次运行趋势对比（后续迭代候选）
- 非测试类质量报告聚合（lint / 安全扫描）
- IM / 邮件推送（Q3）
- 英文模板（Q2，后续候选）

## 5. 关键假设

1. 宿主 Agent 运行时提供后台执行能力（支撑 R2 长任务）。
2. 测试框架已安装于目标项目，Skill 不负责安装框架。
3. 覆盖率产物由框架自身生成，Skill 仅解析不计算覆盖率。
4. 报告面向开发者/QA 本地与 CI 场景，非面向终端用户产品展示。
5. `openspec` CLI 当前不可用，OpenSpec 上下文由本流程手动初始化（`openspec/config.yaml` + `changes/` 结构）。

## 10. 配置项默认值契约（FR4.2 终版）

澄清后确认的配置项默认值，作为 `design.md` 与实现层的契约基线：

| 配置项 | 默认值 | 合法值 | 澄清补充 |
|--------|--------|--------|----------|
| `test_command` | 自动检测 | 任意 shell 命令字符串 | 检测优先级见 FR1.1 |
| `result_file` | 自动检测 | 文件路径 | 仅解析模式生效；执行模式忽略 |
| `output_format` | `markdown` | `markdown` / `html` / `json` | M1 仅 `markdown` 可用；`html`/`json` 为 P1 |
| `output_path` | `reports/` | 目录路径或完整文件路径 | 目录则按默认模板命名；完整路径则直接写入 |
| `coverage` | `auto` | `auto` / `on` / `off` | `auto` 被动检测已有产物；`on` 主动触发带覆盖率命令 |
| `fail_threshold` | 无 | 百分数或小数（如 `80` 或 `0.8`） | M2 交付；低于该值报告结论标记不达标 |

**约束：** 所有配置项均有默认值，用户可覆盖但非必填（G1 一条指令即可完成）。
